# Godot Core System 开源运营策划方案

记录日期：2026-10-06。状态：定位已确认，运营试点待执行。本文件是产品定位和运营计划的维护入口；其中的时间、目标数量与投入额度均为建议，不代表已取得结果或承诺发布时间。

## 1. 项目定位与首轮目标

**为 Godot 独立开发者提供可按需采用的基础系统，减少重复工程，让小型游戏更容易完成和维护。**

产品关键词：轻量、简单但好用、贴近 Godot、明确拥有关系、可运行示例、可靠的失败行为。英文定位：Lightweight foundation systems for Godot indie developers: reduce repeated engineering and make small games easier to finish and maintain.

保留 Godot Core System 名称与仓库地址，先改善价值表达和采用体验。Manager of Managers 是应用服务入口的实现方式，不作为首要宣传卖点；框架的价值由用户减少的工作和实际使用结果证明。

首轮核心问题：外部开发者能否根据公开资料，自主在已有项目中接入一个模块，并在两周后继续使用？

项目作为长期开源品牌主项目；背包插件可提供范围较小的运营经验。五子连珠等主力游戏继续承担作品开发，框架改进尽量来自真实游戏与外部反馈，避免同时启动多个大型重构。

## 2. 用户与价值主张

| 用户 | 典型情境 | 应交付的价值 | 首轮优先级 |
| --- | --- | --- | --- |
| 已掌握 Godot 基础的独立开发者 | 已有玩法，需要补菜单、存档、设置与重开 | 少写重复代码，接入步骤明确，失败可处理 | 核心 |
| 做小型游戏、Game Jam 后继续打磨的开发者 | 原型向可维护作品过渡 | 从一个模块开始，不要求先重组整个游戏 | 核心 |
| 教程学习者和课程作者 | 希望从示例理解系统职责 | 示例与实际版本一致，能看到正确和失败两种结果 | 辅助 |
| C# / Godot .NET 开发者 | 希望采用具有共同语义的模块 | 明确对应版本、依赖、语言差异与覆盖范围 | 按已验证模块纳入 |

首轮不以大型团队、联网复制、服务端权威、完整 ECS 或通用 AAA 架构为承诺范围。项目可以逐步扩展，但必须有真实需求和验收案例。

### 2.1 用户应该能回答的三个问题

1. 这个模块解决了我哪个具体问题？首页用任务和可见效果回答。
2. 我需要改动自己的项目多少内容？文档写出安装、依赖、拥有者与退出清理。
3. 出错和升级时会怎样？文档说明错误结果、状态保留、格式版本及迁移路径。

### 2.2 薄封装的准入标准

新增或强化封装时，说明它减少了什么工作：重复代码、生命周期遗漏、失败处理、配置与恢复或明确的验证负担。仅为原生方法改名，且增加学习成本的接口，不作为独立卖点。

“轻量”的验收依据包括必要接入步骤、模块依赖、强制全局状态、退出清理和替换成本。当前不能笼统声称所有模块零依赖、零侵入或完全可单独打包。

## 3. 产品边界与架构政策

2026-10-07 已建立[模块化重构总览 #104](https://github.com/LiGameAcademy/godot_core_system/issues/104)，复用 #75 的依赖契约，首批执行任务为 #94–#103。目标是独立使用、可选组装与按需分发；运行时热卸载不属于本批范围。Issue 已发布不等于代码已实现，具体依赖和验收以各 Issue 为准。

| 层面 | 框架承担 | 游戏项目承担 |
| --- | --- | --- |
| 应用服务 | 日志、持久化、场景等通用服务的明确入口 | 实际使用方式、跨场景拥有者与配置选择 |
| 局内规则 | 已提炼的状态转换、计时和必要的共同生命周期 | 金币、生命、胜负、奖励、生成与经济规则 |
| 表现 | 可选转场等独立可复用表现 | HUD、美术、声音选择及游戏反馈 |
| 数据 | 类型与格式边界、校验入口、失败结果 | 静态配置、业务 schema、快照编码与迁移 |

Godot 场景、Resource、信号及基础 API 是首选。通用能力优先组合，局内状态由局内拥有者持有；应用级服务可使用 AutoLoad。统一入口不能成为所有对象查找所有依赖的必要通道。

借鉴 Gameplay Framework 时提炼实际职责和寿命，不逐个复制其他引擎类名。能力与 Effect 等专题研究沿用现有项目分工；联网、预测、完整对象注册体系等按后续需求独立评估。

旧管理器继续提供既有扩展；独立 Core 服务拥有单独契约。每项迁移列明替代关系、功能差异、数据格式和修改入口；同一状态禁止由新旧入口同时写入。产品定位调整不自动撤销原版能力的双语言对齐计划。

## 4. 首轮展示模块与采用路径

| 顺序 | 用户任务与展示内容 | 现有起点 | 采用验收 |
| --- | --- | --- | --- |
| 1 | 菜单切到关卡；连点不重复执行；淡入淡出可关闭 | [两场景示例](../examples/native_scenes/README.md) | 正确注册持久拥有者，成功切换，处理 Busy/失败，退出无陈旧回调 |
| 2 | 草稿修改、保存、退出重启后加载；损坏文件不会被当成缺失 | [存档说明与示例](systems/core_save_store.md) | 明确 schema 与版本；区分缺失/损坏；写入失败保留旧档；核对 Windows 扩展 |
| 3 | 捕获按键、提示冲突、取消、恢复默认、重启后保留 | [输入接口](systems/core_inputs.md)与 [input_bindings](../examples/input_bindings/) | 受管动作组明确，冲突不提交，其他动作与手柄事件保留，配置验证后应用 |

上述顺序是传播和采用试点顺序，技术开发仍按宿主路线图推进。存档的原生扩展安装成本须显式测量；导出验收未完成时只演示已验证的编辑器/无界面范围。

会话、事件、状态机和时间作为进阶任务，由真实接入需要推动展示。新会话材料先与对应提交、检查记录核对，再进入正式版本宣传，不将工作区文件存在当成已发布。

### 4.1 首次成功体验的设计目标

- 30 秒：通过截图或短片看懂一个效果和适用任务。
- 5 分钟：从已准备好的发布材料运行一个独立示例。
- 15 分钟：在具备 Godot 基础、环境已就绪的条件下完成一次最小接入。

这些是待测目标。下载与环境准备单独计时，所有需要的准备步骤仍计入记录；不把作者熟练操作时间冒充新用户时间。每次测试记录是否需要维护者逐步帮助。

### 4.2 每个重点模块的交付材料

| 材料 | 内容 | 完成标准 |
| --- | --- | --- |
| 任务页 | 效果、适用情境、边界与入口 | 中英文信息一致，用户能判断是否采用 |
| 最小宿主 | project.godot、安装路径、必要依赖和启动场景 | 从选定发布材料干净获取后可复现；不依赖作者本地资产 |
| 接入说明 | 拥有者、初始化、调用、错误结果、释放 | 能按顺序操作，无隐藏 AutoLoad 或绝对路径 |
| 演示素材 | 一段效果演示及一个失败边界 | 可见行为与该提交一致，不靠剪辑掩盖失败 |
| 检查记录 | 环境、提交、命令、结果和未验收项 | 失败明确阻止对应能力被标为通过 |
| 升级说明 | 旧接口替换、格式变化与回退要求 | 不暗示旧档自动兼容或两语言全面等价 |

复制整个插件到宿主、仅实例化一个服务，与发布独立模块包是不同交付方式。首轮先验证完整插件的必要接入路径，依据卡点再确定独立包装需求。

## 5. README 与文档组织

首页顺序：一句话定位 → 用户任务与效果 → 兼容环境 → 安装 → 最小成功路径 → 详细模块 → 游戏案例 → 反馈与贡献。架构名词放在解释职责的位置。

本轮更新中英文 README 和宿主索引，保留已有模块文档与历史案例入口。正式传播前还需要补齐演示素材、干净宿主和版本验证，不能把文案更新标成这些交付已完成。

维护规则：

1. README 负责引导，模块文档负责 API 与边界，技术路线图负责迁移，本方案负责运营顺序和指标。
2. 新旧接口分别标注；英文首页引用中文计划时标注语言。
3. 兼容记录按版本、操作系统、语言和运行模式维护；编辑器通过与导出通过分别记录。
4. 发布版本说明与本地开发状态分开；例子引用必须与发布包内容一致。
5. 长期旧案例定期核对采用模块与版本，未核对时保持“历史案例”描述。

## 6. 发布准备与发布门槛

首轮定位为采用试点版本。能否称稳定版本，由已验证范围、失败契约和升级兼容性决定；八周结束不自动产生稳定版。

### 6.1 发布前检查清单

- [ ] 固定 GDScript 提交、C# 对应提交与最小共同能力，标明各自独有扩展。
- [ ] 对齐 README、plugin.cfg、版本日志和发布说明中的描述；不擅自改变版本号。
- [ ] 核对现有 Release 与待发布材料，避免“下载最新版”指向旧文档或不存在的包。
- [ ] 从实际候选包建立干净宿主，验证目录、大小写、UID、插件启停与示例启动。
- [ ] 写清每个重点模块的必要依赖，排除开发缓存、宿主业务资源和个人配置。
- [ ] 完成候选范围的行为与失败检查；重开、退出与 A/B 实例案例按实际状态所有权选择。
- [ ] 检查示例素材许可、文档链接和英文关键信息。
- [ ] 发布说明记录不兼容变化、旧存档格式、已知问题、未验收平台与回退步骤。
- [ ] 为实际发行支持范围完成导出验收，并记录原生扩展包含/加载结果。
- [ ] 准备版本化安装路径、升级指南与一个可直接运行的最小示例。

已有宿主记录：用户明确延后 Windows x64 原生存档扩展导出验收，待开发完成后再同意执行。本轮不执行导出；后续沿用该安排。对应验收未完成前不宣传导出包已验证或跨平台可用。编辑器采用试点可以先开展，但必须明确运行范围。

### 6.2 版本与兼容记录模板

| 发布/候选 | GD 提交 | C# 提交 | Godot/.NET | OS/架构 | 编辑器/无界面 | 导出 | 格式与迁移 | 未验收项 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待建立 | 待填 | 待填或不适用 | 待填 | 待填 | 链接到结果 | 待执行/结果链接 | 待填 | 待填 |

修复版本优先保留公开行为。破坏兼容的改动提供迁移说明与明确版本边界；是否保留旧入口依据实际采用记录决定。两种语言不强制使用相同版本号，但对应行为必须可核查。

## 7. 八周采用试点

T0 为维护者实际启动试点的日期，尚未确定；按相对周数安排。单人维护建议每周先保留一个 3–4 小时窗口，包含文档、接入支持和内容整理，技术开发另按已有计划安排。该额度需用首两周记录调整，不增加强制多平台日更任务。

| 阶段 | 建议窗口 | 交付物与动作 | 阶段出口 |
| --- | --- | --- | --- |
| O0 定位落地 | 本轮 | 中英文首页、宿主索引、本运营方案 | 文件可审阅，定位一致，未把计划写成已实现 |
| O1 接入准备 | 第 1–2 周 | 先固定场景模块候选提交与干净宿主；逐项核对安装、依赖和日志；再准备存档与改键材料 | 首个任务可干净复现；三个任务各有公开准备状态与缺口记录 |
| O2 小范围验证 | 第 3–4 周 | 从现有受众中邀请自愿参与者；观察首次接入；修复重复卡点；准备一篇中英文任务指南 | 获得至少 3 份有效尝试记录；失败记录同样保留；不要求三模块齐备才开始 |
| O3 有证据传播 | 第 5–6 周 | 基于通过门槛的模块完成演示与候选发布说明；逐个渠道发布同一主题；收集接入反馈 | 素材指向同一版本和示例；每条宣传都有证据入口；高风险问题未关闭则延后发布 |
| O4 留存与复盘 | 第 7–8 周 | 回访已接入用户；记录继续使用/移除原因；整理案例和升级反馈；决定下一周期 | 指标有分母、证据和未知项，形成继续/收缩/先修接入的决定 |

阶段出口优先于日历。O1 耗时超出两周时收缩到一个展示模块，不跳过接入验证；开发计划仍保留其他模块的进度。外部参与不足时调整触达和任务表达，不把新增模块当成默认解决方法。

## 8. 内容与传播安排

内容从真实解决的问题出发，每个主题共享同一个候选版本、示例与反馈入口。先完成内容资产，再按维护能力选择渠道；平台名单是候选，不代表已经开展发布。

| 主题 | 短演示 | 技术内容 | 最终入口 |
| --- | --- | --- | --- |
| 场景切换 | 成功切换、连点保护、可选淡入淡出 | 为什么服务由持久节点拥有；同步加载的边界 | 对应任务页与两场景宿主 |
| 版本化存档 | 修改草稿、保存、重启读取、失败提示 | 缺失与损坏如何区分；校验和文件替换 | 存档说明与匹配环境的示例 |
| 输入重绑定 | 捕获、冲突、取消、恢复、重启 | 显式动作组与配置提交；保留手柄事件 | 改键说明与示例 |
| 真实项目接入 | 一个已核验的菜单/设置/重开片段 | 游戏规则保留在哪里，哪些重复工作被删去 | 经授权的案例与版本记录 |

每个主题先制作一段 30–60 秒效果演示和一份可照做的任务指南，再按需要扩成长视频。首轮建议每两周完成一个主题，素材来自现有研发，不额外做大型教学游戏。

渠道分工建议：GitHub 保存代码、版本和问题；B站、知乎及现有社群承接中文说明；英文 README 与任务页准备好后，再选择一个海外 Godot 社区或视频渠道试投。涉及社区规则和渠道选择，执行时重新核对，遵守对应社区要求。

行动入口优先引导“运行示例并报告接入结果”。记录用户自愿提供的来源信息及可获取的仓库统计；不能用浏览量、点赞或 Star 冒充采用。

发布文案模板：具体任务 → 可见结果 → 已验证范围 → 示例与版本 → 一个明确的反馈请求。功能广度与架构术语不取代演示。

本方案只准备运营材料。邀请、帖子、邮件、Release、仓库设置或其他外部发布由维护者安排；执行时需要相应发送/发布授权，不因本计划自动发送消息。

## 9. 反馈、社区与贡献维护

每周维护窗口内集中处理一次反馈，不承诺即时客服。先检查信息是否足以复现：版本/提交、Godot 与 OS、模块、最小步骤、期望、实际结果与必要日志。

| 类型 | 处理方式 | 对发布的影响 |
| --- | --- | --- |
| 数据丢失、破坏已有状态、阻止启动 | 优先复现；记录安全回退；修复后验证失败路径 | 阻止受影响能力继续推广 |
| 接入卡点、生命周期或常见失败 | 记录具体步骤；优先修复多次独立出现的卡点 | 影响对应试点阶段出口 |
| 文档、示例与翻译 | 小范围修订并检查对应版本 | 可以成为首批贡献任务 |
| 新功能请求 | 记录真实使用场景、频率、现有替代与维护成本 | 未确认前保留为候选，不自动加入承诺 |

首次贡献优先提供文档修正、可复现失败例子、示例说明和已确认的小修复。每个任务写清入口、预期行为与验证方式；标签是组织工具，不要求现在批量创建 Issue。

真实案例需核对采用模块、版本、持续使用情况和公开展示许可。课程学员、自有项目和独立外部用户分别记录，避免样本重复与熟悉作者带来的偏差。

## 10. 指标、记录与复盘

主要结果是成功接入并继续使用的项目数。Star、Fork、流量和视频播放是辅助关注指标；不能据此推断实际用户数。默认不在插件加入遥测，以自愿反馈、公开案例和手工记录建立试点证据。

| 指标 | 口径 | 首轮建议目标 |

### 10.3 下一周期决定

- 有独立成功接入和继续使用证据：保持小步维护，优先完善用户实际使用的模块。
- 有关注和尝试，但成功少：检查安装、环境、隐藏依赖和示例，不急于扩展宣传。
- 接入成功但很快移除：回访收益不足、API 成本、兼容性与替换原因，修正价值主张。
- 尝试少：核对目标受众和任务表达，做一轮小范围触达；不简单归因为功能不够。
- 维护投入持续超出可用窗口：缩减渠道和公开承诺，集中一个模块；保留缺口记录。

## 11. 内容创作与开源的关系

免费交付应足以让开发者独立安装、运行、接入和理解公开 API。课程可提供完整游戏实践、架构取舍、数值与表现打磨、发行经验和更深入案例，不把基本说明或必要修复放到付费入口之后。

真实游戏发现问题 → 框架沉淀小型能力 → 示例和公开文档说明使用 → 课程讲解项目实践 → 外部采用反馈推动修正。一次研发可以产出多种材料，但模块推广收益和课程转化分别记录。

首轮不以赞助、收费支持或插件商业化为验收目标。后续若有持续采用与明确服务需求，再核对成本和用户需求形成独立方案。
